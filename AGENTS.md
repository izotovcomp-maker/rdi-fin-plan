# Шаблон single-tenant B24 local-app PHP — правила для агента

> **Единый источник правил для любого агента.** Kilo читает этот файл сам;
> Claude Code — через `CLAUDE.md` (там одна строка `@AGENTS.md`). Правила
> правим только здесь и в `docs/agent/`. Слэш-команды живут в `.kilo/commands/`, а
> `.claude/commands` — симлинк на них. Скиллы — в `.claude/skills/`
> (Kilo читает эту папку сам).
>
> **Этот файл — короткое ядро, оно грузится в каждой сессии.** Подробности лежат в
> `docs/agent/` и читаются **по триггеру** (таблица ниже). Карта всех файлов — [docs/INDEX.md](docs/INDEX.md).

Скелет single-tenant B24 local-app: PHP-бэк (>=7.4, без composer и фреймворков), vanilla JS + CSS без
bundler'а, файловый store без БД (`data/`, защита `<?php exit;?>`, без `.htaccess`), B24 OAuth
(токены в `data/b24-tokens.php`). Полное описание каркаса — [README.md](README.md).

**Tenant-режим зафиксирован:** single-tenant. Multi-tenant (маркет, N порталов одним
деплоем, white-label) — **смена шаблона**, не доработка этого.

## Старт сессии

**На приветствие и общий разговор ничего не читай** — просто ответь. Файлы открывай,
когда пришёл **рабочий запрос**:

- **Вопрос «как устроено / как сделать»** (как задеплоить, как вызвать REST, что значит X) —
  ответь по правилам из таблицы ниже. Онбординг не навязывай: упомяни одной фразой, что он не пройден,
  и всё.
- **Просьба что-то сделать с проектом** (сделай, задеплой, добавь, поправь):
  1. Есть ли `.onboarding-done` в корне проекта?
     - **Нет** → *«Давай быстро настроим проект — задам несколько вопросов.»* и дальше по [docs/onboarding.md](docs/onboarding.md).
     - **Есть** → прочитай [docs/state.md](docs/state.md) (где мы сейчас) и [docs/project-brief.md](docs/project-brief.md),
       а если есть `source/INDEX.md` — и его. Работай в рамках проекта.
  2. Вопросы задавай, только если без ответа нельзя продолжить и вывести его из проекта
     (`docs/project-brief.md`, `source/`, кода) невозможно. Не спрашивай то, что уже известно.

Сам шаблон (папка `tmpl-*`, без `.onboarding-done`) — это не проект: в нём обсуждаем и правим
правила, **онбординг не запускаем и не деплоим**. Онбординг и деплой — только в проекте, скопированном
из шаблона (slug деплоя = имя папки проекта).

## Деплой — только по явной цели

Деплой на `prod` / `customer` выполняй, только если **человек в этой сессии назвал цель** (проект/slug и
профиль). «Задеплой» без цели — не повод угадывать: спроси, куда. Условия деплоя не выполнены
(не та папка, нет slug, нет профиля) — **остановись и спроси**; не подгоняй обходом (копии папок под
нужный slug, переименования). Токены и секреты на сервере не читай и не печатай.

Данные конкретного проекта (название, клиент, портал, плейсменты, cron, прод URL, скоупы)
**не хранятся в этом файле** — только в `docs/project-brief.md`; его заполняет онбординг.
Материалы заказчика — в `source/` (новый материал → строка в `source/INDEX.md`).

## Поиск по Б24 — жёсткое правило

**Первое действие на любой вопрос про Б24 — `grep` по INDEX.md правил (шаг 1). Вызов MCP или ответ
по памяти до этого запрещены**, даже если ответ кажется очевидным. Порядок обязателен, шаги не
пропускаются, не гадай (полная версия — [docs/agent/b24-search.md](docs/agent/b24-search.md)):

1. **Правила:** `grep -i "<слово>" /projects/docs/rules-b24/INDEX.md` (синонимы: `batch`, `scope`, `token`…); нашёл — читай файл правила целиком и строй ответ от него.
2. **Клон документации:** `grep -rn "<термин>" /projects/docs/b24-rest-docs --include="*.md"`.
3. **MCP `bitrix24-docs`:** только если 1–2 не дали ответа. Ошибка параметров — исправь и повтори; пустая выдача не доказывает отсутствие.
4. **Онлайн-ссылки:** последний шаг.

Код шаблона (`b24()`, `storeRead`, `accessAllows`) ищи в `www/`, а не в документации Б24.

## Железные правила кода (всегда, без чтения файлов)

- REST — только через `$b24 = b24(); $b24->call(...)`. **Не CRest и не прямой curl.** CRM — `crm.item.*` с `entityTypeId`, не legacy `crm.deal.*`.
- N id → **`$b24->batch([...])` чанками по 50**, не `foreach` с `call`.
- State — только `storeRead(FILE)` / `storeWrite(FILE, $data)` в `data/`; секреты и токены в git не кладём.
- «Авторизован на портале Б24» ≠ «можно всё»: проверка доступа внутри приложения — на нашем коде (`accessAllows()`).
- Остальное и обоснования — [docs/agent/dev-rules.md](docs/agent/dev-rules.md).

## Журнал проекта и коммиты — главное правило

Ведём **журнал**, чтобы проект можно было передать другому исполнителю без потери
контекста: что делали, где сейчас, куда идём. Память проекта — пять файлов (роли и правила
вставки — [docs/INDEX.md](docs/INDEX.md)): `handoff`, `project-brief`, `state`, `changelog`, `decisions`.
`changelog.md` и `decisions.md` — только дописываются (append-only), место вставки — по маркеру
`<!-- Новые ... добавляй ... -->` в начале файла.

**После каждого осмысленного шага** (добавили фичу, починили баг, задеплоили, приняли решение,
закончили сессию; не каждую строчку):

1. Обнови `docs/state.md` — где сейчас и что дальше.
2. Допиши `docs/changelog.md` — одна запись про шаг.
3. Был неочевидный выбор? — запись в `docs/decisions.md` (D-NNN).
4. Снимок в git: `bash scripts/snapshot.sh "<что сделали>"`.

Слэш-команды делают всё это сами: `/log` · `/decision` · `/handoff`.
