# Макет приложения

Макет — статичный интерфейс на вымышленных данных, который согласует человек (и при необходимости
заказчик) **до** бэка и привязки к порталу. Протокол — [../onboarding.md](../onboarding.md), «Фаза 3».

## Структура

```
mock/
├── index.html      ← разметка; ссылки только относительные
├── mock-data.js    ← вымышленные данные (подключаются тегом <script>, не fetch)
├── mock.js         ← отрисовка и интерактив в памяти (без запросов к серверу)
└── css/style.css   ← копия www/css/style.css (обновляется скриптом сборки)
```

Папка лежит **вне `www/`** — `deploy.sh` её не выкладывает. Заготовка уже есть в шаблоне —
перепиши её под проект, не создавай рядом вторую.

## Требования

- **Самодостаточность.** Открывается двойным кликом по `index.html`: без PHP, сервера, CDN,
  внешних шрифтов и `fetch`. Всё, что нужно, лежит внутри `mock/`.
- **Стиль — «тёплая бумага»** из `www/css/style.css`: токены в `:root`, моноширинные заголовки,
  чёрные обводки KPI, вкладки, таблицы с числовыми колонками `.num`, плашки стадий `.stage-badge`.
  Новые цвета — только токенами в `style.css`, не по месту. Так макет совпадает с итоговым
  приложением, а то, что утвердили на макете, не переделывается при переносе в `www/`.
- **Обязательная плашка** `.demo-banner`: «макет на вымышленных данных, портал не подключён» +
  что именно просим проверить + кнопка «Сбросить макет».
- **Вымышленные данные.** Правдоподобные названия, суммы, даты, статусы; есть пустые, очень
  длинные и отрицательные значения. **Никаких** реальных данных клиента, ФИО, токенов, ссылок на
  внутренние документы — архив уходит заказчику.
- **Поля = поля Б24 или свои из плана.** Для каждой колонки знай источник; сомнения — в вопросы.
- **Экраны и состояния** из согласованного плана: список, карточка, фильтры, пустое состояние,
  ошибка, окно «Доступ». Интерактив — только в памяти (правка поля, смена стадии, сортировка).
- **Вкладка «Как это считается»** — если в приложении есть расчёты: откуда берутся цифры,
  формула, какие поля Б24 используются. Заказчик сверяет по ней логику.
- Стадии и справочники с цветами из портала в макете — ориентировочные; пометь это в плашке.

## Показ человеку

1. Основной способ: `mock/index.html` в браузере — дай полный путь и список экранов.
2. Окружение умеет браузер/скриншоты — покажи скриншотом ключевые экраны.
3. Локальный сервер не обязателен: `php -S localhost:8080 -t mock` — на крайний случай.
4. Хостинг макета на сервере — только по явной команде человека (макет в `www/` не класть).

## Пересылка заказчику

`bash scripts/pack-mock.sh [версия]` → `mock-<версия>.zip` в корне проекта (в git не попадает).
Скрипт сам подтягивает свежие стили. Заказчику: «распакуйте и откройте `index.html`».
Правки заказчика вноси в макет и пересобирай под новым номером (`v2`, `v3`). Согласование
заказчика = согласование макета; зафиксируй его в `docs/decisions.md`.

## После согласования

Пересмотри план и список прав (макет мог добавить или убрать поля и сущности), обнови
`docs/project-brief.md`, затем переноси вёрстку в `www/template.html` и `www/js/app.js`.
Папку `mock/` оставь в репозитории как эталон согласованного вида.
