## 2026-10-09 — «По объекту»: без автозагрузки, пустой список до выбора объекта
- Вкладка «По объекту» открывается с пустым полем «— выберите объект —» и без данных; загрузка только после выбора объекта (запрос заказчика)
- Переключатель «В реализации» / «Завершено» / «Все» целиком перестраивает список и сбрасывает выбор — выбранный объект больше не «прилипает» к чужому фильтру
- Правки/индикатор сбрасываются вместе с выбором; после правок и по «Обновить» данные объекта перезагружаются, только если объект выбран

## 2026-10-09 — Объекты: воронка «Преддоговорная» вне финплана, сортировка по коду, переключатель статусов
- Объекты из воронки «Преддоговорная» (движений денег нет) исключаются из финплана: бэк определяет id воронки по подстроке имени через `crm.category.list` (id категорий не константа), fallback — ничего не исключать; сделки нужны и для списка стадий своих воронок (переключатель статусов)
- «По объекту»: селект объектов отсортирован по коду (числовая сортировка, 0002 < 0010), то же в фильтре «Объект» на других вкладках
- «По объекту»: переключатель «В реализации» / «Завершено» / «Все» (по умолчанию «В реализации»); «Завершено» = терминальные стадии (semantics S/F), стадия сделки приходит в P.stages; выбранный объект остаётся в списке даже если не подходит под фильтр
- Проверено: php -l, node --check, 26 юнит-проверок (вкл. finSkipDealCategoryIds) — зелёные; задеплоено на prod

## 2026-10-09 — UX правок «По объекту»: цельное поле даты, счётчик по полям, индикатор отправки
- Поле «Дата план» переведено с нативного `input[type=date]` (в iframe Б24 сегменты дд/мм/гггг ломают ввод) на цельное текстовое с маской: точки сами, понимает 12.08.2026 / 12082026 / 120826; кривая дата при выходе из поля откатывается
- Счётчик на кнопке подтверждения считает изменённые ПОЛЯ (у одного платежа дата+стадия = 2), а не платежи
- Вместо «Данные обновляются…» в каждой строке при отправке — один индикатор «Идет обновление 🔄» на месте кнопок; поля на время отправки задизейблены
- Проверено: node --check, юнит-проверки маски/парсера даты — зелёные; задеплоено на prod

## 2026-10-09 — «По объекту»: накопление правок и отправка одной кнопкой (D-011)
- Правки даты/примечаний/стадии больше не уходят в CRM сразу: строка помечается плашкой «✍», наверху вкладки — «✅ Подтвердить и отправить все изменения (N)» и «❎ Отменить изменения» (перезагрузка данных объекта); возврат поля к исходному снимает пометку
- Бэк `plan-update.php` переведён на пачку `{items:[...]}`: валидация всех правок (batch `crm.item.get`, стадии своей воронки) до записи, затем batch `crm.item.update` чанками по 50; ошибка одной правки отменяет всю пачку (D-011)
- После отправки данные перезагружаются через ~1.5с (БП пересчитывает периоды/остатки асинхронно)
- Проверено: php -l, node --check — зелёные; поведение на живом портале проверяет человек (стадии `crm.item.update` в Y-режиме — D-008)
- Связанные решения: D-008, D-011

## 2026-10-09 — Период платежа из поля портала «Период план»
- Жалоба «столбики графика в 2607, а фин движения в другом месяце»: приложение считало период от «Дата план» (D-004), но у платежей есть поле «Период план» (ГГММ), которое ведёт БП, а дату БП переписывает при оплате → расхождение на месяц
- Бэк: период нормализуется из `UF_CRM_12_PAY_PLAN_PERIOD`/`UF_CRM_20_SCPAY_PLAN_PERIOD` с fallback на дату (`finNormPeriod`, D-010); фронт `periodOf` использует `p.period` — график, матрица, реестр, KPI считаются от периода портала
- Ограничение: серверный фильтр from/to пока по «Дата план» (дефолт «с начала года» не задевает) — D-010
- Проверено: php -l, node --check, 25 юнит-проверок — зелёные; задеплоено на prod
- Связанные решения: D-004, D-010
