# Журнал решений

> Здесь — **почему** проект устроен так, а не иначе. Каждое значимое
> решение: что выбрали, какие были варианты, почему именно это.
> Файл **только дописывается** (новые записи — вниз). Старые записи не
> удаляем: если решение отменили — добавляем новую запись «отменяет D-NNN».
>
> Зачем: чтобы следующий исполнитель не «переоткрывал» уже закрытые вопросы
> и не ломал то, что сделано осознанно. Один абзац здесь экономит часы.

Записывай решение, когда выбор был **неочевидным** или у него есть
последствия: скоупы, структура данных, плейсменты, обход бага и т.п.

## D-004 · Макет не делаем — ТЗ уже согласовано с заказчиком в другом проекте
**Дата:** 2026-10-09 · **Статус:** принято

**Контекст.** По порядку работы после плана полагается макет в `mock/`. Но интерфейс
финплана уже был сделан и согласован с заказчиком в другом проекте — прототип
`source/fin-plan-demo.html` (вкладки «Свод по месяцам», «Реестр движений»,
«По объекту», «Как это считается»; согласованные решения перечислены прямо в нём).
**Решение.** Фаза 3 (макет) пропускается: `fin-plan-demo.html` = утверждённый макет.
Бэк и фронт делаются «в похожем виде» — вёрстка и логика демо переносятся в
`www/template.html` + `www/js/app.js`.
**Последствия.** Блок B (деплой/привязка) можно выполнять по готовности бэка
без отдельного согласования макета. Папка `mock/` шаблона не используется.

## D-005 · Фильтр периода: по умолчанию с января текущего года, без верхней границы
**Дата:** 2026-10-09 · **Статус:** принято

**Контекст.** Портал молодой (платежей в перспективе ≤ сотни), истории прошлого года
по умолчанию не нужно. Тысяч платежей не будет, но выгружать всю историю каждый раз
бессмысленно.
**Решение.** Выборка платежей из Б24 и фильтр UI по умолчанию: от 1 января текущего
года, окончание не ограничено («всё, что от начала и старше ничего»). Другой период
пользователь выбирает явно фильтром.
**Последствия.** REST-выгрузка ограничена датой снизу (`>=01.01 тек. года` по
«Дата план»); старые данные подгружаются только явным выбором периода. Свод, реестр
и график работают в рамках выбранного периода.

## D-006 · Все неоплаченные платежи = «План»
**Дата:** 2026-10-09 · **Статус:** принято

**Контекст.** У Оплат есть промежуточные стадии (Закр Готовы → Счёт отправлен → …),
у Расход(П) — свои (Ожидание документов → Ожидание оплаты). Вопрос: как показывать
промежуточные стадии в финплане.
**Решение.** Для режима «факт/план» бинарно: факт = финальная стадия («Счёт оплачен»
для 1046 / «Оплачено» для 1062), всё остальное = «План». Промежуточные стадии не
откатываются и не учитываются как факт (поведение демо подтверждено заказчиком).
**Последствия.** Логика `isPaid` в фронтенсе/бэке проверяет только финальную стадию
(`SUCCESS`); бейдж стадии в «По объекту» остаётся информационным.

## D-007 · Имена UF-полей Б24 — только оригинальные капсом, без camelCase
**Дата:** 2026-10-09 · **Статус:** принято

**Контекст.** `crm.item.*` по умолчанию отдаёт пользовательские поля в camelCase
(`ufCrm8OCode`), и в прошлых проектах агент уже пытался так их писать — это
повторяющаяся ошибка: реальные имена полей на портале капсом (`UF_CRM_8_O_CODE`),
camelCase-варианты ломают select/filter и путают при сверке со справками.
**Решение.** Все вызовы `crm.item.*` в проекте идут с `useOriginalUfNames=Y`,
в `select`/`filter`/`fields` — только оригинальные имена капсом из `source/RDI *.md`
(константы в `www/api/fin-config.php`). camelCase остаётся только у стандартных
полей (`stageId`, `categoryId`, `parentId1038`) — это не UF-имена.
**Последствия.** Любой новый эндпоинт проекта следует тому же правилу. При
пополнении справок полей — имена копировать капсом дословно.

## D-008 · `crm.item.list` + `useOriginalUfNames=Y`: select через `*`, стандартные поля — чтение в обоих регистрах
**Дата:** 2026-10-09 · **Статус:** принято (обход фактического поведения портала)

**Контекст.** На реальном портале `ooordi` выяснилось (через `api/plan-debug.php`):
при `useOriginalUfNames=Y` метод `crm.item.list` из `select` молча выбрасывает все
стандартные поля — и в camelCase (`id`, `stageId`), и капсом (`ID`, `STAGE_ID`) —
проба с чисто стандартным select вернула 16 пустых объектов. UF-поля при этом
приходят исправно. Документация такого не описывает (заявлено, что параметр влияет
только на UF-имена).
**Решение.** Все выборки смартов идут `select: ['*']` + `useOriginalUfNames=Y`:
UF-поля приходят капсом (D-007), стандартные поля читаются через `finItemField()`
в обоих регистрах. Элементы списка лежат в `result.items` (не в `result`).
**Почему.** Один вызов вместо двух, объёмы малые (≤ 50 элементов на страницу),
.camelCase-режим по умолчанию не используем — заказчик требует капс-имена UF.
**Последствия.** Фильтры по стандартным полям в Y-режиме не проверялись — при
появлении такой потребности сначала проба через `plan-debug.php`. `crm.item.update`
шлёт поля капсом (`STAGE_ID` + UF капсом) — работу правки стадии проверяем вручную
на портале (B8), при отказе портала — пересмотреть. `plan-debug.php` держим в бою,
пока идёт отладка на реальных данных.

## D-009 · Вкладка «По объекту» не зависит от периода; выборка по объекту — с локальной перепроверкой фильтра
**Дата:** 2026-10-09 · **Статус:** принято (запрос заказчика 2026-10-09)

**Контекст.** Вкладка «По объекту» наследовала серверный фильтр периода из
`plan.php` (D-005): при периоде «с начала 2026» объекты со старыми платежами
показывались пустыми. Заказчик: по выбранному объекту показывать ВСЕ его платежи,
независимо от периода на других вкладках.
**Решение.** Новый эндпоинт `api/plan-object.php?deal=<id>`: все платежи сделки
(доходные по `PARENT_ID_1038`, расходные по подрядам `PARENT_ID_1058` + привязанные
к самой сделке), её подряды и стадии — без фильтра дат. Фронт грузит данные объекта
отдельно от `plan.php` (периодные вкладки не меняются), перезагружает только при
смене объекта, правке платежа и по «Обновить».
**Почему так.** Фильтры по стандартным полям в Y-режиме не проверены (D-008) и
портал может молча их игнорировать — результат каждой выборки перепроверяется
локально (`finItemsByParent`), при ошибке фильтра — выборка без него и локальный
срез. OR-фильтр для Расход(П) заменён двумя прямыми запросами с дедупликацией —
предсказуемее, чем непроверенная логика OR в Y-режиме.
**Попутно найдено.** Сбор stageId для списка стадий в `plan.php` читал только
camelCase (`$p['stageId']`), а портал в Y-режиме отдаёт капс (`STAGE_ID`) — список
стадий был пуст, реестр и «По объекту» показывали сырые statusId без цветов портала
(жалобы заказчика на «не человеческие статусы» и «неверные стадии»). Исправлено
через `finItemField()`; в `plan-debug.php` добавлена проба фильтра `PARENT_ID_1038`.

## D-002 · Переезд хостинга на VPS + Caddy + PHP-FPM
**Дата:** 2026-07-03 · **Статус:** отменяет хостинг-часть D-001

**Контекст.** D-001 фиксировал хостинг как Netangels (shared, `.htaccess`).
Команда перешла на собственный VPS с Caddy + PHP-FPM для всех B24-приложений.

**Варианты.** Остаться на shared-хостинге (Netangels) vs собственный VPS с
явной настройкой каждого проекта через Caddyfile.

**Решение.** VPS, домен `b24.blackboxbegin.space`, один Caddy-блок `handle
/<slug>*` на проект, деплой — локальный rsync (`bash deploy.sh`) прямо на
сервере, без SSH.

**Почему.** Больше контроля над PHP-FPM/Caddy-конфигом, не завязаны на
ограничения конкретного shared-хостера. Caddy не читает `.htaccess` —
защита state осталась той же (`<?php exit;?>`-префикс), это не пришлось
менять.

**Последствия.** `.htaccess`-независимость шаблона (D-001) оказалась кстати:
переезд не потребовал менять модель защиты. Появились новые следствия
Caddy `uri strip_prefix` — APP_URL нужно править вручную после `init.php`,
handler URL обязательно с `/index.php`, `template.html` вместо `index.html`.
Все зафиксированы в `CLAUDE.md` → «Caddy + PHP-FPM — следствия для шаблона».
Домен, а не IP — при смене хостера под тем же доменом менять ничего не
нужно; деплой на сервер заказчика с другим доменом — отдельный кейс,
не покрыт этим решением.

## D-003 · env.php генерируется deploy.sh, init.php — только для 1%-кейса
**Дата:** 2026-07-04 · **Статус:** принято, уточняет D-002

**Контекст.** После D-002 конвент деплоя зафиксирован: домен всегда
`b24.blackboxbegin.space`, путь всегда `/var/www/b24/<slug>`. При этом
`APP_URL`/`APP_PATH`/`DATA_ROOT` стали полностью детерминированы из
одного значения (slug), но флоу продолжал требовать открыть `init.php`
в браузере и вручную поправить `APP_URL` (следствие `uri strip_prefix`
из D-002). На практике оба реальных проекта на VPS (`ap-simple-test`,
`fv-taskindep-panel`) этот шаг обошли — `env.php` был написан вручную
напрямую, `init.php` на сервере не оказывалось вообще (`deploy.sh` его
и не копирует, см. `--exclude 'init.php'`), задокументированный флоу
не воспроизводим на свежем сервере как описано.

**Варианты.** (а) Почистить `deploy.sh`, чтобы `init.php` таки доезжал
до сервера при первом деплое — оставить flow как есть. (б) Убрать
`init.php` из основного flow, генерировать `env.php` детерминированно
прямо в `deploy.sh`, оставить `init.php` в шаблоне только как fallback
для хостинга, где путь/домен заранее не известны (shared-хостинг
заказчика, FTP).

**Решение.** (б). `deploy.sh` при первом деплое slug'а (env.php на
сервере ещё нет) генерирует `env.php` из `env.example` подстановкой
`APP_URL=https://b24.blackboxbegin.space/<slug>`, `APP_PATH=DEPLOY_DIR`,
`DATA_ROOT=DEPLOY_DIR/data`. Человеку остаётся вписать только
`B24_CLIENT_ID`/`SECRET` — их и так нельзя получить иначе, кроме как
из карточки local-app в Б24. `init.php` физически остаётся в шаблоне
(`www/init.php`) как есть, без изменений — для кейса, где конвент
VPS+Caddy не применим (хостинг заказчика с непредсказуемым путём).

**Почему.** Автоопределение `APP_URL` через `init.php` было нужно для
общего случая (произвольный shared-хостинг, куда шаблон изначально
целился) — на своём VPS с фиксированным конвентом это лишний шаг,
который к тому же не работал как описано (см. «Контекст»). Убирать
`init.php` из репозитория целиком не стали — шаблон должен оставаться
пригодным не только для нашего VPS.

**Последствия.** `how-to-link.md` описывает только 99%-кейс (наш VPS,
`deploy.sh`). Новый файл `how-to-link-ALL.md` — процедура для 1%-кейса
через `init.php`, на него ссылаются `how-to-link.md`, `README.md`,
`CLAUDE.md`. `docs/state.md`-чеклист (шаблонный, наследуется новыми
проектами) обновлён под новый flow.
