# ПЕРЕДАЧА ПРОЕКТА — ЧИТАЙ ЭТО ПЕРВЫМ

> Этот файл — точка входа для **новой нейронки** (или человека), которая
> впервые открывает проект. Цель: за 5 минут понять **что это, где мы
> сейчас и куда идём** — без необходимости читать весь код.

---

## Как устроена память проекта

Весь контекст живёт в четырёх файлах. Читай их **в этом порядке**:

| # | Файл | Отвечает на вопрос | Как меняется |
|---|------|--------------------|--------------|
| 1 | [project-brief.md](./project-brief.md) | **Что** это за проект и **зачем** | Редко |
| 2 | [state.md](./state.md) | **Где мы сейчас** и **что делать дальше** | Постоянно — «живой снимок» |
| 3 | [changelog.md](./changelog.md) | **Что уже сделали** (по датам) | Только дописывается вниз |
| 4 | [decisions.md](./decisions.md) | **Почему** так, а не иначе | Только дописывается вниз |

Плюс [../AGENTS.md](../AGENTS.md) — инструкции по стеку, деплою и правилам работы.
Если есть `source/INDEX.md` — это описание входного контекста проекта (макеты, спецификации, материалы заказчика); прочитай и его.

---

## Быстрый старт для входящей нейронки

1. Прочитай 4 файла выше по порядку.
2. Глянь последние коммиты:
   ```bash
   git log --oneline -20
   ```
3. Проверь что прод живой — открой URL из раздела «Карта проекта» в `state.md`.
4. Возьми первый пункт из «Следующие шаги» в `state.md` — и продолжай.

**Что работает прямо сейчас:** прод задеплоен и привязан к порталу; свод (график+матрица), реестр с режимом правки даты, «По объекту» без автозагрузки с переключателем «В реализации/Завершено/Все» и плитками распределения (✔️/❓), KPI «По периоду»/«Факт», накопление правок «✍» с batch-отправкой, стадии с именами/цветами портала, период из поля БП «Период план»; доступ по отделам с переключателем у админа.
**Что в процессе / недоделано:** ждём замечаний заказчика по предварительному блоку; не проверены на живом портале `crm.item.update` со `STAGE_ID` в Y-режиме (D-008) и фильтр по стандартному полю `PARENT_ID_1038` (проба `pay_by_deal_1046` в «Диагностике»); правка полей самой сделки/подряда — не делалась, уточнить у заказчика; после приёмки убрать `api/plan-debug.php`.
**Прод URL:** https://rub24.blackboxbegin.space/rdi-fin-plan/
**Хостинг / slug:** prod (`iagdeploy@rub24.blackboxbegin.space:/var/www/b24`), slug: `rdi-fin-plan`, профиль деплоя в `.deploy-target` (= prod), деплой `bash deploy.sh`.
**Главные подводные камни:** B24 OAuth двухфазный install-flow (`state`+`installFinish`); при `useOriginalUfNames=Y` стандартные поля приходят КАПСОМ и молча выпадают из `select` — читать через `finItemField()`, UF-поля только капсом (D-007/D-008); стадии смартов — в `STATUS_ID` полной строкой `DT{ety}_{cat}:...`, не в `ID` (D-009); период платежа — поле БП «Период план», не «Дата план» (D-010); Caddy `uri strip_prefix` — handler URL заканчивается на `/index.php`; все REST через `$b24->call()`, N id — batch по 50; доступ «кто что может» — на нашем коде (`accessAllows()`).
**Первое, что стоит сделать новому исполнителю:** прочитать `project-brief.md` → `state.md` → `decisions.md` (D-004…D-011), взять первый пункт «Следующих шагов» в `state.md` (разбор обратной связи заказчика по предварительному блоку).
