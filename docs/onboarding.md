# Протокол онбординга

> Читается один раз — при первом запуске нового проекта, скопированного из
> шаблона `tmpl-b24-php-kilo`, пока не создан `.onboarding-done`.
> После онбординга этот файл больше не нужен для работы — можно оставить
> как есть (не мешает) или удалить.

Задавай вопросы **строго по одному**. Если ответ очевиден из контекста — уточни, не пропускай.

**Куда идут ответы.** Данные проекта пишутся **только** в
[project-brief.md](./project-brief.md). `AGENTS.md` онбординг не правит — там
правила шаблона, общие для всех проектов.

## Вопрос 1 — Название и суть
*"Как называется проект и что он делает? Одной-двумя фразами. Для какого клиента?"*

*(Пример: «Пульт сделок — дашборд аналитики CRM для менеджеров, клиент ООО Ромашка»)*

**Куда пойдёт ответ:** `docs/project-brief.md` → «Общее»: Название, Описание, Клиент
(если клиент не назван — оставь «—»).

## Вопрос 2 — Вводные файлы
*"Есть ли исходные материалы по проекту: макеты и скриншоты страниц, спецификации,
документация по данным портала, пожелания заказчика? Если есть — положи в папку `source/`."*

Варианты:
- *Да, я сложил материалы в `source/`*
- *Нет, пропускаем*

**Если «Да»:**
1. Прочитай все файлы в `source/` (кроме `.gitkeep` и `INDEX.md`). Текст и
   изображения читай сам. Видео, архивы и очень большие PDF целиком не читай —
   опиши по имени, размеру и тому, что удалось увидеть, и пометь «не прочитан целиком».
2. Создай `source/INDEX.md`: таблица **Файл · Что это · Чем полезно (фронт / бэкенд /
   данные) · Прочитан**. Содержимое файлов не копируй — только описание и
   что из него следует для проекта.
3. Если по материалам остались вопросы, которые нельзя снять самому, —
   задай их заказчику после онбординга, не в его середине.

**Если «Нет»:** `source/INDEX.md` не создавай.

**Куда пойдёт ответ:** `source/INDEX.md` (создаётся при «Да») и
`docs/project-brief.md` → «Входной контекст» (статус «есть» / «нет»).
Агент найдёт материалы сам: `AGENTS.md` велит читать `source/INDEX.md`, если он есть.

## Вопрос 3 — Портал Б24
*"На каком портале Битрикс24 работает клиент?"*

*(Пример: company.bitrix24.ru)*

**Куда пойдёт ответ:** `docs/project-brief.md` → «Общее»: Портал Б24. Только как
справка: домен портала приложение получает само при установке, на код ответ не влияет.
Если клиент ещё не определился — запиши «не определён».

## Вопрос 4 — Плейсменты
*"Где откроется приложение в Битрикс24?"*

Варианты:
- **LEFT_MENU** — пункт в левом меню (дефолт, уже настроен в `www/api/bind.php`)
- **CRM_DEAL_DETAIL_TAB** / **CRM_CONTACT_DETAIL_TAB** — вкладка в карточке сделки / контакта
- **CRM_DETAIL_ACTIVITY** — виджет активности в карточке CRM
- **Несколько** — укажи список

**Куда пойдёт ответ:** `docs/project-brief.md` → «Технические параметры»: Плейсменты.
Для не-дефолтных плейсментов раскомментируй их в `www/api/bind.php` и проверь
нужные скоупы в `docs/project-brief.md` → «Скоупы Б24».

## Вопрос 5 — Нужен ли cron?
*"Нужна ли фоновая обработка данных (cron-задача)?"*

- **Нет** → удаляю `www/bin/process.php` из проекта
- **Да** → оставляю, заполняю `runJob()` по ходу работы

**Куда пойдёт ответ:** `docs/project-brief.md` → «Технические параметры»: Cron
(«нет» или «да»); при «нет» — удаление `www/bin/process.php`.

## Вопрос 6 — Куда деплоим
*"Куда будем деплоить приложение?"*

Варианты:
- **PROD — свой боевой сервер Б24-приложений** (**по умолчанию**; выбирай, если заказчик
  не просил иначе или ответ «не знаю»). Данные сервера уже в `/projects/mydeploy.env`.
- **Сервер заказчика** — приложение живёт у заказчика (по SSH). Нужны данные его сервера.
- **LAB — учебный сервер** — только для тренировки.

**Куда пойдёт ответ:**
- файл `.deploy-target` в корне проекта: `prod` | `customer` | `lab` (коммитится);
- `docs/project-brief.md` → «Технические параметры»: Хостинг, Прод URL;
- `how-to-link.md` — агент переписывает заготовку под этот проект
  (правила — [deploy-targets.md](./deploy-targets.md)).

**Если PROD или LAB:** профиль берётся из `/projects/mydeploy.env`. Проверь, что файл
есть (нет — `mydeploy.env.example` в корне шаблона), и выполни
`bash deploy.sh --dry-run`: убедись, что URL и каталог верные.

**Если «сервер заказчика»:** веди по [deploy-targets.md](./deploy-targets.md), раздел
«Профиль customer»: опроси заказчика, дай ему команды для пользователя `iagdeploy`,
после ответа заполни `deploy.customer.env`. Пока данных сервера нет — оставь в
`.deploy-target` значение `customer` и отметь в `docs/state.md` → «Открытые вопросы»,
что ждём данные от заказчика; `how-to-link.md` перегенерируй, как только они придут.
Если у заказчика нет SSH (только FTP/панель) — ручной сценарий, `how-to-link-ALL.md`.

## Что не спрашиваем — заполняется сам

| Поле в `project-brief.md` | Значение |
|---|---|
| Дата старта | сегодняшняя дата |
| Хостинг / slug | slug = имя папки проекта; хостинг — по ответу на вопрос 6 |
| Прод URL | `PUBLIC_BASE_URL` выбранного профиля + `/<slug>/` |
| Скоупы Б24 | `crm user placement department`; дополнительные дописывай, когда добавляется фича (`lists`, `task` и т.д.) |
| Особенности | по ходу работы |

## После всех ответов

1. Заполни `docs/project-brief.md` по соответствию выше («Общее», «Технические
   параметры», «Входной контекст»).
2. Если на вопрос 2 был ответ «Да» — убедись, что `source/INDEX.md` создан.
   Запиши ответ на вопрос 6 в `.deploy-target` и перегенерируй `how-to-link.md`
   (метки `{{...}}` — по таблице из `deploy-targets.md`).
3. Обнови `docs/state.md` — скорректируй «Следующие шаги» под конкретный проект.
4. Если cron не нужен — удали `www/bin/process.php`.
5. Создай пустой файл `.onboarding-done` в корне проекта.
6. Снимок в git: `bash scripts/snapshot.sh "онбординг: <название проекта>"`.
7. Скажи, что настроено и что нужно дальше (обычно: `bash deploy.sh` → создать
   local-app в Б24 → вписать CLIENT_ID/SECRET в `env.php`).
