# Протокол онбординга

> Читается один раз — при первом запуске нового проекта, скопированного из
> шаблона `tmpl-b24-php-kilo`, пока не создан `.onboarding-done`.
> После онбординга этот файл больше не нужен для работы — можно оставить
> как есть (не мешает) или удалить.

Задавай вопросы **строго по одному**. Если ответ очевиден из контекста — уточни, не пропускай.

**Куда идут ответы.** Данные проекта пишутся **только** в
[project-brief.md](./project-brief.md). В `AGENTS.md` онбординг правит
только первую строку (заголовок, см. A.7) — остальное там правила шаблона, общие для всех проектов.

## Вопрос 1 — Название и суть
*"Как называется проект и что он делает? Одной-двумя фразами. Для какого клиента?"*

*(Пример: «Пульт сделок — дашборд аналитики CRM для менеджеров, клиент ООО Ромашка»)*

**Куда пойдёт ответ:** `docs/project-brief.md` → «Общее»: Название, Описание, Клиент
(если клиент не назван — оставь «—»).

## Вопрос 2 — Вводные файлы
*"Есть ли исходные материалы по проекту: макеты и скриншоты страниц, спецификации,
документация по данным портала, пожелания заказчика? Если есть — положи в папку `source/`."*

Варианты:
- *Да, я сложил материалы в `source/`*
- *Нет, пропускаем*

**Если «Да»:**
1. Прочитай все файлы в `source/` (кроме `.gitkeep` и `INDEX.md`). Текст и
   изображения читай сам. Видео, архивы и очень большие PDF целиком не читай —
   опиши по имени, размеру и тому, что удалось увидеть, и пометь «не прочитан целиком».
2. Создай `source/INDEX.md`: таблица **Файл · Что это · Чем полезно (фронт / бэкенд /
   данные) · Прочитан**. Содержимое файлов не копируй — только описание и
   что из него следует для проекта.
3. Если по материалам остались вопросы, которые нельзя снять самому, —
   задай их заказчику после онбординга, не в его середине.

**Если «Нет»:** `source/INDEX.md` не создавай.

**Куда пойдёт ответ:** `source/INDEX.md` (создаётся при «Да») и
`docs/project-brief.md` → «Входной контекст» (статус «есть» / «нет»).
Агент найдёт материалы сам: `AGENTS.md` велит читать `source/INDEX.md`, если он есть.

## Вопрос 3 — Портал Б24
*"На каком портале Битрикс24 работает клиент?"*

*(Пример: company.bitrix24.ru)*

**Куда пойдёт ответ:** `docs/project-brief.md` → «Общее»: Портал Б24. Только как
справка: домен портала приложение получает само при установке, на код ответ не влияет.
Если клиент ещё не определился — запиши «не определён».

## Вопрос 4 — Плейсменты
*"Где откроется приложение в Битрикс24?"*

Варианты:
- **LEFT_MENU** — пункт в левом меню (дефолт, уже настроен в `www/api/bind.php`)
- **CRM_DEAL_DETAIL_TAB** / **CRM_CONTACT_DETAIL_TAB** — вкладка в карточке сделки / контакта
- **CRM_DETAIL_ACTIVITY** — виджет активности в карточке CRM
- **Несколько** — укажи список

**Куда пойдёт ответ:** `docs/project-brief.md` → «Технические параметры»: Плейсменты.
Для не-дефолтных плейсментов раскомментируй их в `www/api/bind.php` и проверь
нужные скоупы в `docs/project-brief.md` → «Скоупы Б24».

## Вопрос 5 — Нужен ли cron?
*"Нужна ли фоновая обработка данных (cron-задача)?"*

- **Нет** → удаляю `www/bin/process.php` из проекта
- **Да** → оставляю, заполняю `runJob()` по ходу работы

**Куда пойдёт ответ:** `docs/project-brief.md` → «Технические параметры»: Cron
(«нет» или «да»); при «нет» — удаление `www/bin/process.php`.

## Вопрос 6 — Куда деплоим
*"Куда будем деплоить приложение?"*

Варианты:
- **PROD — свой боевой сервер Б24-приложений** (**по умолчанию**; выбирай, если заказчик
  не просил иначе или ответ «не знаю»). Данные сервера уже в `/projects/mydeploy.env`.
- **Сервер заказчика** — приложение живёт у заказчика (по SSH). Нужны данные его сервера.
- **LAB — учебный сервер** — только для тренировки.

**Куда пойдёт ответ:**
- файл `.deploy-target` в корне проекта: `prod` | `customer` | `lab` (коммитится);
- `docs/project-brief.md` → «Технические параметры»: Хостинг, Прод URL;
- `docs/how-to-link.md` — агент переписывает заготовку под этот проект
  (правила — [deploy-targets.md](./deploy-targets.md)).

**Если PROD или LAB:** профиль берётся из `/projects/mydeploy.env`. Проверь, что файл
есть (нет — `mydeploy.env.example` в корне шаблона), и выполни
`bash deploy.sh --dry-run`: убедись, что URL и каталог верные.

**Если «сервер заказчика»:** веди по [deploy-targets.md](./deploy-targets.md), раздел
«Профиль customer»: опроси заказчика, дай ему команды для пользователя `iagdeploy`,
после ответа заполни `deploy.customer.env`. Пока данных сервера нет — оставь в
`.deploy-target` значение `customer` и отметь в `docs/state.md` → «Открытые вопросы»,
что ждём данные от заказчика; `docs/how-to-link.md` перегенерируй, как только они придут.
Если у заказчика нет SSH (только FTP/панель) — ручной сценарий, `docs/how-to-link-ALL.md`.

## Что не спрашиваем — заполняется сам

| Поле в `project-brief.md` | Значение |
|---|---|
| Дата старта | сегодняшняя дата |
| Хостинг / slug | slug = имя папки проекта; хостинг — по ответу на вопрос 6 |
| Прод URL | `PUBLIC_BASE_URL` выбранного профиля + `/<slug>/` |
| Скоупы Б24 | `crm user placement department`; дополнительные дописывай, когда добавляется фича (`lists`, `task` и т.д.) |
| Доступ к приложению | по умолчанию — по отделам (`DEFAULT_ACCESS_MODE`, отдел по умолчанию `DEFAULT_ALLOWED_DEPARTMENTS` = `[1]`, «Администрация»). Режим (по отделам / персонально / всем) и списки администратор меняет сам кнопкой «Доступ» в приложении — в онбординге не спрашиваем |
| Особенности | по ходу работы |

## После всех ответов

Порядок проекта: **ответы → саммари и план (согласует человек) → макет (согласует человек)
→ бэк и данные → деплой и привязка к порталу**. Привязка идёт после макета, потому что
только тогда известно, какие сущности и права нужны (подробности — «Привязка к порталу — когда» ниже).

Блок A агент выполняет сразу. Фазы 2 и 3 — следом, каждая заканчивается согласованием
с человеком. Блок B (деплой и подключение к порталу) агент **переносит в
`docs/state.md` → «Следующие шаги»** чек-листом `[ ]` с пометкой «агент» / «человек» —
но выполняет его **только после согласования макета**. Блок C — постоянные правила.

### A. Агент, сразу после ответов

1. Заполни `docs/project-brief.md`: «Общее», «Технические параметры»,
   «Входной контекст».
2. Вопрос 2 «Да» — убедись, что `source/INDEX.md` создан.
3. Запиши ответ на вопрос 6 в `.deploy-target`.
4. Прикинь **предварительный** список прав из «Скоупы Б24» в брифе и ответа на вопрос 4.
   Окончательный список ты составишь по согласованному плану (какие сущности реально
   нужны) — и назовёшь его человеку на шаге B5, а не сейчас.
5. Данные деплоя уже есть (`prod`, `lab`)? — перегенерируй `docs/how-to-link.md`
   (метки `{{...}}` — по таблице в [deploy-targets.md](./deploy-targets.md)).
   Данных нет (`customer`)? — запиши в state задачу B0.5 и не гадай значения.
6. Cron не нужен — удали `www/bin/process.php`.
7. Переименуй первую строку `AGENTS.md`
   (`# Шаблон single-tenant B24 local-app PHP — правила для агента`) в
   `# <Название проекта> — правила для агента`. Больше ничего в `AGENTS.md` не трогай.
8. Создай пустой файл `.onboarding-done` в корне проекта.
9. Снимок в git: `bash scripts/snapshot.sh "онбординг: <название проекта>"`.
10. **Не начинай деплой и привязку к порталу.** Переходи к «Фазе 2 — саммари и план»
    (ниже). Привязка (блок B) — только после согласованных плана и макета.

### Фаза 2 — саммари и план (сразу после блока A, в чате)

Не переходи к макету и коду, пока человек не согласовал план. Напиши в чат:

1. **Что я прочитал и как понял.** Суть проекта, для кого, какие материалы из `source/`
   прочитаны (по `source/INDEX.md`), что из них следует. Отдельно — **допущения** и
   **что осталось непонятным** (вопросы человеку, если без ответа нельзя продолжить).
2. **Какие данные Б24 нужны.** Сущности (сделки, контакты, смарт-процессы, пользователи,
   отделы…), поля, методы REST — по документации (`b24-search.md`, шаг «клон документации»),
   без обращения к порталу. Отсюда — **предварительный список прав** («Настройка прав»).
3. **План реализации по шагам:** экраны, API-эндпоинты, хранение в `data/`, плейсменты, cron,
   доступ. Порядок: макет → бэк → деплой/привязка. Для каждого шага — что получит человек.
4. **Риски и открытые вопросы.**

Закончи фразой: *«Согласуй план или поправь — после этого делаю макет.»* Правки человека
внеси в план и покажи снова. Согласованный план запиши в `docs/state.md`
(«Следующие шаги») и в `docs/decisions.md`, если выбор неочевиден.

### Фаза 3 — макет с произвольными данными (после согласования плана)

Сначала **предложи** макет — человек может отказаться, если проект тривиальный. Цель:
увидеть интерфейс и состав данных до того, как пишется бэк и трогается портал, — на макете
переделывать дёшево, на рабочем портале дорого. Макет можно показать заказчику.

Все правила — в [agent/mockup.md](agent/mockup.md) (прочитай перед работой). Главное:

- Статичный и самодостаточный: `mock/index.html` + `mock-data.js` + `mock.js` + `css/`; открывается
  двойным кликом, без сервера. Стиль «тёплая бумага» из `www/css/style.css`. Папка вне `www/` — в прод не уходит.
- Вымышленные данные, плашка «макет, данные вымышлены», все экраны и состояния плана.
- Покажи человеку (путь к `index.html` + список экранов, скриншоты, если есть браузер) и попроси
  проверить: **что лишнее, чего не хватает, верны ли названия и порядок**. Правки вноси, пока не скажет «согласовано».
- Для заказчика: `bash scripts/pack-mock.sh` → `mock-v1.zip`; правки — новая версия.
- После согласования: **пересмотри план и список прав**, обнови `docs/project-brief.md`
  («Скоупы Б24», «Плейсменты») и `docs/state.md`, снимок в git. Затем переноси вёрстку в
  `www/template.html` + `www/js/app.js` и пиши бэк по плану.

### Привязка к порталу — когда

Блок B (деплой, local-app, `client_id/secret`, установка) — **после согласования макета**
(или плана, если человек отказался от макета). Тогда известны сущности и точный список прав.

Привязка раньше допустима только по явному решению человека — например, нужны реальные
данные портала (пользовательские поля `UF_*`, воронки и стадии, смарт-процессы), которых нет
в документации. **Важно:** агент сам REST-запросы к порталу выполнять не может — токены лежат
на сервере в `data/b24-tokens.php` (их агент не читает), а `www/api/debug.php` открывается
только в браузере с сессией администратора. Поэтому реальный ответ портала снимает
**человек** через `debug.php` и вставляет JSON в чат. Если такой нужды нет — не привязывай
вслепую до макета.

(на сервере заказчика — ещё и админ заказчика).

**B0. Только для `customer` (сервер заказчика):**

| B0.1 | Задать заказчику вопросы по серверу (список — `deploy-targets.md`, «Что спросить у заказчика») | агент → человек | вопросы человек отправляет заказчику |
| B0.2 | Дать готовые команды для пользователя `iagdeploy` (с публичным ключом) | агент → человек | человек отправляет их заказчику; ключ — публичная часть `~/.ssh/iagdeploy_ed25519.pub` |

### C. Постоянные правила для каждого проекта

- **Права в карточке приложения.** Каждый раз, когда просишь создать или изменить
  приложение, называй человеку точный список прав для «Настройка прав».
  Добавилась фича с новым скоупом — скажи, какое право добавить, и что после этого
  нужно обновить токен (см. [rule-b24-scope-add-needs-token-refresh](/projects/docs/rules-b24/rule-b24-scope-add-needs-token-refresh.md)).
- **Перед каждым деплоем в прод** — проход по [rule-b24-security-baseline](/projects/docs/rules-b24/rule-b24-security-baseline.md).
- **Реальный деплой на `prod` и `customer`** — только по явной команде человека; сначала `--dry-run`.
- **После каждого осмысленного шага** — `/log`.
