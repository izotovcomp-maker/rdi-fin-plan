## Где мы сейчас

Приложение работает на prod (`https://rub24.blackboxbegin.space/rdi-fin-plan/`), local-app привязан к `ooordi.bitrix24.ru`. За сессию отлажено на живых данных и допирано по обратной связи заказчика:

- **Стадии/статусы** — человеческие имена стадий и цвета плашек портала (два слоя бага: сбор stageId капсом, D-008; поле `STATUS_ID` у `crm.status.list`, D-009).
- **«По объекту»** — данные грузятся отдельным запросом `api/plan-object.php` без периода; вкладка открывается с пустым списком, объект выбирается вручную; сортировка по коду; переключатель «В реализации / Завершено / Все»; воронка «Преддоговорная» исключена из финплана.
- **Период платежа** — из поля портала «Период план» с fallback на дату (D-010) — график/матрица/реестр считаются от периода БП.
- **Правки** — накапливаются с пометкой «✍», отправляются одной пачкой (batch `crm.item.update`, D-011): и на «По объекту» (дата/примечания/стадия), и в реестре (режим «✍ Режим правки даты», только дата). Маска даты — цельное поле ДД.ММ.ГГГГ / 120826.
- **KPI** — сводные плитки «По периоду» и «Факт» (Доход/Расход/Сальдо в одну строку).
- **Плитки распределения** — по сделке («Цена контракта» `UF_CRM_8_O_COST` − доходы) и по каждому подряду (цена − Расход(П)): «✔️ Распределено» / «❓ Не распределено {сумма}» с точностью до копеек.

Всё задеплоено (`bash deploy.sh`, профиль prod), юнит-проверки бэка зелёные.

## Открытые вопросы / блокеры

- `crm.item.update` со `STAGE_ID` капсом в Y-режиме не проверен на живом портале — правки стадий уходят пачкой, при отказе портала — переключить update на дефолтный режим (D-008).
- Фильтр периода (с/по) на сервере по «Дата план»: при узких периодах оплаченный платёж с плановым периодом БП может не попасть в окно (D-010) — перевести фильтр на «Период план», если заказчик начнёт пользоваться узкими периодами.
