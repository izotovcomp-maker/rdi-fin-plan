# Безопасность B24 local-app — на что не защищает OAuth и что проверять всегда

## Статус

Справочник, не разовая проверка. Применять:
- сразу после онбординга, **перед** тем как проектировать архитектуру первой
  фичи (не после того, как код уже написан) — см. CLAUDE.md, раздел
  «БЕЗОПАСНОСТЬ»;
- при добавлении каждого нового класса функциональности (новый API-эндпоинт,
  плейсмент, cron, вебхук, загрузка файлов, вызов стороннего платного API);
- перед каждым `bash deploy.sh` в прод.

Источник: официальные рекомендации Битрикс24
([`settings/cloud-and-on-premise/security-recommendations.md`](https://github.com/bitrix-tools/b24-rest-docs/blob/main/settings/cloud-and-on-premise/security-recommendations.md)
в локальном клоне `b24-rest-docs`) + общий чек-лист уязвимостей вайб-кодинга
(`dev-portal/result/safety-points.md`), адаптировано под архитектуру именно
этого шаблона.

## Главный факт архитектуры, который меняет всё

Личность подтверждает Битрикс: при каждом открытии iframe приходит `AUTH_ID`
текущего юзера, шаблон бьёт им в `user.current` и получает ID + отдел (см.
[rule-b24-department-based-access](rule-b24-department-based-access.md)) —
подделать нельзя, токен реальный, выпущен Битриксом.

Но **все бизнес-вызовы к CRM в этом шаблоне идут не через токен текущего
юзера, а через один общий admin-токен**, сохранённый один раз при установке
(см. [b24-local-app-tokens-save-only-on-install](b24-local-app-tokens-save-only-on-install.md)).
Отсюда:

- **Кто это** — знает Битрикс, проверено криптографически.
- **Что этому конкретному человеку можно** — знает только код этого проекта.
  Битрикс это не ограничивает никак: раз общий токен даёт полный доступ к
  CRM, приложение физически может отдать любые данные любому, кто прошёл
  идентификацию, если само не проверит.

Практический вывод: «пользователь авторизован на портале Б24» закрывает
форму входа и подбор пароля — и только их. Всё, что происходит на VPS дальше
запроса, защищено ровно настолько, насколько это написано в коде проекта.

## Точки риска — что применимо к этому шаблону, что нет

**1–2. Форма входа / пароли.** Не применимо. Входа своего нет, авторизация
целиком на стороне портала Б24.

**3. Секреты.** `B24_CLIENT_ID`/`SECRET`, `data/b24-tokens.php`. Не в git
(уже в `.gitignore` по шаблону), не во фронтенд-код. Засветились — перевыпустить
в карточке local-app, не просто спрятать.

**4. IDOR / доступ по чужому id.** Актуально в полный рост — см. факт
архитектуры выше. Любой `www/api/*.php`, отдающий или меняющий данные по id
(будь то запись в `data/`, будь то CRM-сущность), проверяет принадлежность
объекта текущей сессии/отделу, а не только то, что сессия валидна.

**5. Спрятанная кнопка ≠ защита.** Гейт на уровне «открыть приложение
целиком» уже реализован (`session.php`+`access.php`, см.
[rule-b24-department-based-access](rule-b24-department-based-access.md)).
Но это гейт входа, не гейт каждого действия. Любое отдельное админ-действие
**внутри** уже открытого приложения — своя проверка `requireAdminSession()`
или отдела на сервере, не сокрытие кнопки в JS.

**6. Инъекции.** Классический SQL неприменим — нет БД, файловый стор.
Эквивалент того же класса дыры: путь/имя файла в `data/`, собранные из
пользовательского ввода → path traversal. Не собирать путь конкатенацией
с id/именем без валидации (allowlist `[a-zA-Z0-9_-]`, никаких `../`,
никаких сырых имён из `$_POST`/`$_GET` напрямую в `fopen`/`file_put_contents`).

**7. Вебхуки / входящие события.** Шаблон сейчас **не регистрирует**
event-обработчики (`OnCrm*` и т.п.) — только опциональный cron
(`www/bin/process.php`), который сам инициирует запросы, а не принимает их.
**Если добавляете обработчик события** — обязательна проверка
`application_token` на каждый входящий вызов, сверка с тем, что сохранён
для этого `member_id` при `OnAppInstall`. Без неё на handler URL можно
постучаться напрямую и подделать событие — тот же класс риска, что
неподписанный вебхук оплаты. Алгоритм — официальные доки, раздел
«Проверяйте application_token в событиях»
(`security-recommendations.md` в клоне `b24-rest-docs`). Та же проверка
нужна для любой будущей интеграции с оплатой.

**8. Зависимости.** Стек «без composer» (см. CLAUDE.md, СТЕК) — риск почти
снят по умолчанию. Добавляете пакет (composer или npm для сборки фронта) —
проверить, что проект живой и без известных CVE, прежде чем тянуть.

**9. XSS в выводе.** Если где-то показываете текст, который ввёл пользователь
портала (комментарий, название, что угодно из формы или полученное из CRM
как есть) — экранировать при выводе в `template.html`/JS, не вставлять через
`innerHTML` без экранирования.

**10. CORS.** Приложение живёт в iframe на своём origin, кросс-доменных
fetch с фронта обычно нет — риск низкий по умолчанию. Актуально, только
если добавляете отдельный публичный API-эндпоинт, вызываемый не из своего
же фронта (интеграция со сторонним сервисом и т.п.) — тогда конкретный
список доменов, никогда `*`.

**11. Загрузка файлов.** В шаблоне из коробки нет — актуально, только если
фича её добавляет. Тип по содержимому, не по расширению; переименовывать
при сохранении; класть вне пути, откуда сервер исполняет PHP.

**12. Гонки состояний.** **Особенно актуально именно для этого шаблона**:
файловый стор (`storeRead`/`storeWrite` в `data/`) без БД — значит нет
транзакций и блокировок из коробки вообще. Фича вида «списать/применить
один раз», счётчик, бронирование слота — нужен явный `flock()` вокруг
чтения-изменения-записи, иначе два одновременных запроса (две вкладки, два
юзера) гонятся и оба проходят.

**13. Supabase/Firebase RLS.** Не применимо — стор свой, файловый.

**14. Лимиты на платные API.** К самому REST Б24 не применимо — у него
свой троттлинг (`503 QUERY_LIMIT_EXCEEDED`, см. официальные доки, раздел
«Учитывайте лимиты REST API»), это вопрос устойчивости, не бюджета.
Актуально, если добавляете вызовы к **стороннему** платному API (модель,
SMS, генерация картинок) по действию пользователя портала — свой лимит на
юзера в сутки и общий потолок расхода, Б24 тут ничем не поможет.

## Смежные рекомендации из официальных доков, не входящие в исходный чек-лист

- **HTTPS без исключений** — не отключать проверку SSL-сертификата в бою,
  только на локальной отладке.
- **Минимально необходимый scope** — не добавлять права «про запас», см.
  уже действующий принцип шаблона «параметры собираются лениво по факту
  запроса» (CLAUDE.md).
- **Логи без секретов** — `access_token`/`refresh_token` в логах только
  замаскированными (первые символы + `***`), не целиком.
