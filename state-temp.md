# state-temp — рабочая записка по отработке шаблона

> **Правило.** Пока шаблон не отработан, этот файл обновляется постоянно: после каждого
> осмысленного шага (что сделали, что решили, на чём остановились, что дальше).
> Читай его первым, если продолжаешь работу над шаблоном. Когда шаблон будет готов —
> содержимое разнесём по `docs/` (решения → `decisions.md`, история → `changelog.md`),
> а файл удалим.
>
> Это записка для работы **над шаблоном**, а не журнал будущих проектов: журнал проектов —
> `docs/state.md` и остальные файлы `docs/`, их не трогаем.

**Последнее обновление:** 2026-10-07

## 1. С чем работаем

- **Репозиторий:** `/templates/tmpl-b24-php-kilo` — шаблон single-tenant B24 local-app на PHP
  (PHP без composer, vanilla JS, файловый store `<?php exit;?>`, деплой rsync).
- **Происхождение:** ядро `www/` — оригинал `_b24-single-php` от команды интеграторов
  (платформа dima.z: KB в `/data/kb`, Netangels, Apache, `deploy-prod.sh`, `.portal-meta.json`).
  Поверх: журнал проекта из VibeCode-шаблона (`docs/*`, `/log`, `/decision`, `/handoff`,
  `snapshot.sh`), инфраструктура нашего VPS (Caddy), `rules/`, слой для Kilo.
  Оригиналы лежали в `source/` для сравнения; сейчас папка пуста (`.gitkeep`).
- **Цель:** универсальный шаблон (и проекты на его основе), который можно вести **разными
  харнессами и моделями** на одном и том же проекте, чтобы подобрать оптимальную связку.
  Первый на очереди — **Kilo Code**; затем Claude Code (уже работает) и другие.
- **Серверы:**
  - `prod` — боевой, `rub24.blackboxbegin.space` (45.91.55.178): Ubuntu 24.04, Caddy,
    PHP 8.3-fpm (`www-data`), `/var/www/b24/<slug>`, rsync есть, блок `@blocked` в Caddy есть.
  - `lab` — этот учебный VPS (`b24.blackboxbegin.space`), деплой локальный.
  - `customer` — сервер заказчика, SSH + rsync, пользователь `iagdeploy`.
- **Данные серверов** — в `/projects/mydeploy.env` (вне git), образцы в корне шаблона.

## 4. Задачи

### Задача 1. Реальный деплой на rub24 (**следующая**)

Цель: убедиться, что `deploy.sh` с профилем `prod` реально работает на боевом сервере
(до сих пор проверен только `--dry-run`; ветки `ssh` — на loopback).

**Что требуется:**
1. **Команда владельца** на реальный деплой (без неё на prod ничего не заливаем).
2. **Тестовый slug** — одноразовый (например `zz-tmpl-test`): копия шаблона в папке с таким именем.
3. Профиль на месте: `/projects/mydeploy.env` (есть), `iagdeploy` проверен (есть),
   `bash deploy.sh --dry-run` чист (был чист).
4. **Блок Caddy** — вставляет владелец под `deploy` (у `iagdeploy` прав нет), `deploy.sh`
   напечатает готовый блок; затем перезагрузка Caddy (`sudo caddy reload --config /etc/caddy/Caddyfile`).
5. **Проверки после деплоя** (read-only, я могу выполнить):
   - `curl -I https://rub24.blackboxbegin.space/<slug>/` → PHP отвечает (ожидается 403-страница
     «Доступ запрещён», раз открыто не из Б24);
   - `.../<slug>/data/` и `.../<slug>/env.php` → 404 (блок `@blocked`) или пустой ответ;
   - на сервере: `env.php` `640 iagdeploy:www-data`, `data/` `2770`, каталоги `2755`, файлы `644`;
   - повторный `bash deploy.sh` не трогает `env.php`.
6. **Необязательно, глубже:** тестовый портал Б24 — зарегистрировать local-app (шаги в
   `how-to-link.md`), вписать `B24_CLIENT_ID/SECRET` в `env.php` на сервере, открыть из портала —
   проверит install-flow и запись PHP-FPM в `data/`. Нужен: портал, где можно создать
   local-app, и решение, оставлять ли тестовое приложение.
7. **Уборка** после теста: удалить каталог slug на сервере (владелец — `iagdeploy`, может сам),
   владелец удаляет блок из Caddyfile и перезагружает Caddy; если регистрировали app — удалить в Б24.

**Открытые вопросы к владельцу для этой задачи:** имя тестового slug; нужен ли тест с порталом
Б24; кто и когда вставляет блок Caddy.

### Бэклог (унаследовано от оригинала, пока не решали)
- `www/api/debug.php` доступен любому с сессией (`requireSession`), а не только админу, и лежит в проде.
- Первая установка: токены сохраняются из любого POST с `AUTH_ID/REFRESH_ID` без проверки
  `application_token`/`member_id`.
- Файловый store без блокировок (`flock`): гонки на `sessions.php` и параллельный refresh токена.
- CSRF: сессия принимается из cookie (`SameSite=None`), `Content-Type`/`Origin` не проверяются.
- PHP `>=7.4` (EOL), на серверах 8.3 — можно поднять планку.
- На rub24 у пользователей `claude` и `deploy` фактически права root (sudo без пароля) — осознать риск.
- 7 проектов на rub24 принадлежат `deploy`; `iagdeploy` их перезаписать не может
  (при желании: `sudo chown -R iagdeploy:www-data /var/www/b24/<slug>`).
- Рассмотреть `from="<IP>"` в `authorized_keys` ключа `iagdeploy` (если у этой машины постоянный IP).
- `docs/handoff.md`: написано «четыре файла» и «changelog дописывается вниз» — по правилам
  файлов пять, changelog — новое сверху.
- Для `rules/b24-iframe-x-frame-options-csp.md` секция «На этом VPS (…)» привязана к учебному серверу.
